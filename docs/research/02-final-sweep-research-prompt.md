# FINAL CONSOLIDATION SWEEP: SAGE engine + Fragment Foundry platform

Produce a single blueprint that locks down architecture, tooling, formats, and build order. This is the last research pass before implementation begins.

## Context (established in prior work — build on this, do not re-derive it)

A prior first-principles research report on "what a modern MUD engine should be in 2026" concluded: a small genre-agnostic core (entities + components + rules/systems + event bus + containment/space graph + identity/permissions + scheduler/world clock + event-sourced persistence with snapshots); everything genre-specific (combat, levels, classes, magic, economy, factions, weather) is an optional installable module; untrusted community code runs sandboxed (WASM with capability-based host imports and fuel metering); the browser client is driven by structured out-of-band data (GMCP/MSDP lineage) so text and rich panels coexist; AI is an optional layer (authoring assistance, dynamic dialogue/narration, automated playtesting agents) with deterministic fallbacks and never the system of record; creation tiers must coexist (visual/config/natural-language for laypeople, scripting and full APIs for developers) rather than convert one-way; open-core, self-hostable, non-extractive (Foundry VTT model, not Roblox). Precedents studied: MUD1/AberMUD/TinyMUD/LPMud/DikuMUD/LambdaMOO, Evennia, Ranvier, Foundry VTT, Roblox, Minecraft Forge/Fabric fragmentation, Twine/Ink, Colyseus/Nakama, Stanford Generative Agents (Smallville), AI Dungeon failures.

The developer is a single independent creator (Python, TypeScript, Next.js, Supabase, ComfyUI experience) who builds with AI coding assistants (Claude Code). He previously built SAGE v1 (github.com/Fablestarexpanse/sage-engine: Python/FastAPI, Redis live state + PostgreSQL persistence, 4 Hz tick, YAML world packages, sealed plugin API, three clients — React player client, Nexus admin console, Tauri WorldForge editor — plus MCP map tools; licensed FSL-1.1-ALv2). He is scrapping it and starting from a clean repo.

Lessons from v1's decision log that the new design must avoid:
1. The engine was extracted out of an existing game rather than a game dropped into a platform, producing endless rename shims, migration exceptions, and an "invariant ratchet" fighting hardcoded setting terms.
2. Two sources of truth (Redis live state flushed to Postgres every ~60 s) caused silent edit reverts.
3. No real entity/component model — a per-character "stats blob" with plugin seals and per-world key declarations was a workaround, and half the decision log patched it.
4. Three clients and an MCP surface were built before the world model was stable.
5. Cross-plugin dependencies (shops needing wallets needing agents) were handled ad hoc.
6. Proprietary game content got entangled with engine code and public git history.
7. Licensing ambiguity (FSL "competing use" clause vs. the promise that others can build and sell worlds on it).

Ideas from v1 to CARRY FORWARD as principles: "LLMs describe what happened; deterministic code decides what happens"; sealed plugin API (a module declares what it touches and fails at boot otherwise); a lexicon layer where every player-facing string is overridable per world; content schema exported so editors generate forms; "some world runs with zero AI" as a CI invariant; per-account AI credit ledger for generated media; synthetic agents (computer-controlled persistent characters who own shops, hold wallets, act and remember) as the engine's defining feature.

From a second project (github.com/Fablestarexpanse/CharacterBinder, MIT): Tavern Card v2 PNG embedding (Base64 JSON in a PNG tEXt chunk, keyed chunks per card type), a `cardShape` importer that infers a payload's type from its structure rather than trusting its label, a platform-compatibility panel that shows what a target will drop before export, version-as-new-record, and an MCP bridge with mutual-HMAC pairing so an AI agent can author cards into a local-first browser library (IndexedDB, WebLLM in-browser sorting).

## Locked decisions (research must respect these)

1. **SAGE** (Synthetic Agent Game Engine) is the engine. Open-core, self-hosted by users on their own servers. Fragment Foundry never runs worlds.
2. **Fragment Foundry** is the website: (a) engine distribution; (b) fragment registry/marketplace; (c) browser-based, local-first creation tools that export fragment files (CharacterBinder pattern — nothing leaves the machine); (d) a social layer — creator accounts, profiles, follows, likes, comments, collections, changelogs; (e) an opt-in heartbeat world directory (running servers ping the site with world manifest + player count, the site lists a connect link); (f) later, sales of resources (paid fragments, tipping/bounties) — sequenced after the social layer.
3. **"Fragment" is the unit of sharing.** Two packaging types under one vocabulary. **Content fragments** (data the engine already interprets — agents/NPCs, rooms, zones, items, quests, lorebooks, rulesets-as-config, whole-world cover cards) can be PNG cards with embedded JSON, Tavern-card-compatible where sensible so existing character cards on Chub/SillyTavern import as agents. **Code fragments** (mechanics/plugins) are proper signed packages with manifests, semver, dependency resolution, and WASM sandboxing — never code inside images. Content fragments may declare code-fragment dependencies, so "drop the PNG in" installs the data and prompts to fetch the module.
4. **Everything is manifest-driven.** The engine emits a machine-readable self-description per release (e.g. `sage describe --json`: version, core components, plugin API surface, shipped tools, event types, capabilities, docs). Every fragment carries a manifest (kind, version, engine-compat range, dependencies, capabilities, declared commands/panels/components/config, creator, license, derived_from for remix attribution). The Foundry site, the player client, and the editors all render from these manifests; the site is never allowed to know something a manifest doesn't say.
5. **Synthetic agents are first-class entities**, not a bolt-on plugin with its own tables: an entity with a "mind" component that drives the SAME command interface a player uses; memory derived from the event log; persona/goals as data; swappable drivers (scripted, LLM, hybrid); Smallville-style memory-stream/retrieval/reflection where LLM-driven.
6. **Build order** (bottom-up, the opposite of v1): entity/component model → event log + single persistence path → plugin seal/module system → agents → then clients/editors. Do not build editors before the world model is stable.
7. Marketing line to preserve: "Worlds are built, not scripted" (data-first). Avoid "room-based" as an engine description; space is a graph.

## What this sweep must research and decide

**A. Concrete stack for a solo AI-assisted developer.** Evaluate honestly for THIS person: Rust (Bevy-style ECS, Wasmtime host), Elixir/BEAM, TypeScript/Node, and Python. Weigh: solo maintainability, AI-coding-assistant effectiveness per language, WASM host maturity, ECS libraries (bevy_ecs, flecs, hecs, becsy, miniplex, esper, etc.), event-store options (EventStoreDB, Marten/Postgres event tables, SQLite event log, NATS JetStream, custom append-only on Postgres), single-source-of-truth persistence patterns that avoid v1's Redis/Postgres split, hot reload, embedded scripting for creators (Lua via WASM, JS via QuickJS/Boa, Rhai, Starlark, Luau), and browser client transport (WebSocket now, WebTransport later). Recommend one primary stack and one fallback, with reasoning and a migration risk assessment. Consider whether the engine could itself run in the browser (WASM) for the Foundry's "try before you download" and for the in-browser editors sharing engine validation code.

**B. Manifest and fragment format specification.** Study npm package.json, Cargo.toml, Foundry VTT module.json/system.json, Minecraft mod manifests (Fabric mod.json, NeoForge), VS Code extension manifests, OCI image manifests, Debian control files, and Tavern Card v2/v3 specs. Propose: (1) the engine self-description schema; (2) the fragment manifest schema covering both content and code fragments; (3) the PNG content-fragment encoding (chunk keywords, size limits, tEXt vs iTXt vs zTXt, how to stay Tavern-compatible for agent cards while carrying SAGE-specific extensions, how `cardShape`-style structural detection should work); (4) the code-fragment package format (archive layout, WASM component model vs core WASM, WIT interfaces, capability declarations); (5) dependency resolution and semver policy; (6) signing and provenance (Sigstore/cosign, minisign, SLSA, npm provenance; how Foundry VTT and Roblox verify packages); (7) migration hooks for event-sourced state when a fragment upgrades.

**C. Sandboxing and the plugin seal.** Wasmtime vs Wasmer vs wazero vs browser WASM; fuel/epoch interruption; memory limits; capability-based host imports; how "declare what you touch or fail at boot" maps to WIT/component-model imports; performance overhead for hot-path systems (combat resolution each tick); whether a trusted first-party native tier is needed; how Roblox Luau, Foundry VTT (unsandboxed JS), Minecraft, and Godot GDExtension handle trust — and what went wrong.

**D. Synthetic agent architecture.** Generative Agents (Park et al. 2023) and follow-ups (2024–2026): memory stream, retrieval, reflection, planning; cost and latency control (local models via Ollama/LM Studio/llama.cpp, batching, tick-aligned thinking budgets, cheap heuristic drivers with LLM escalation); how agents share the player command interface; persisting agent memory in an event-sourced world (memory as projections over the event log, embeddings/vector store as a rebuildable cache, never canonical); Tavern card fields mapped to a mind component; guardrails against prompt injection from player chat; determinism/replay implications; how to make agents work with zero AI (behavior trees / utility AI / GOAP fallbacks).

**E. Fragment Foundry site architecture.** Given the developer's Next.js/Supabase familiarity: registry design (static-first; object storage like Cloudflare R2/S3 + CDN; Supabase Postgres for metadata; search via Postgres FTS/Meilisearch/Typesense); how npm, crates.io, PyPI, Foundry VTT's package listing, Nexus Mods, CivitAI, and Modrinth are architected; upload pipeline that validates manifests server-side using the SAME code the engine uses (shared validation package compiled to WASM/JS); the `sage install <fragment>` client protocol; heartbeat world directory (study Minecraft server lists, MUD Connector, Grapevine, Steam server browser, Mudlet's directory) including anti-spoofing, rate limits, and privacy; social features (accounts via Supabase Auth/Clerk, profiles, follows, comments, collections, moderation of listings, DMCA/takedown, AI-generated-content policy lessons from CivitAI); browser-based creation tools that are local-first (IndexedDB/OPFS, optional WebGPU local models), exporting fragments, possibly running the engine's validation or a mini engine in WASM; how the site renders pages from manifests (docs generation, feature grids, compatibility badges); marketplace layer (Stripe Connect vs Lemon Squeezy vs Paddle as merchant of record, tax, payouts, low payout floors, tipping/bounties, license-gated authenticated downloads — no DRM; lessons from Roblox concentration, itch.io, Gumroad, CivitAI Buzz).

**F. Licensing.** Analyze FSL-1.1-ALv2 vs Apache-2.0 vs MIT vs AGPL vs BSL/Elastic/SSPL for the engine, and separately for first-party plugins, the reference world, fragment templates, and the Foundry site code. Specifically resolve: can users build and SELL worlds/fragments on SAGE without ambiguity under each option? What must the fragment manifest's license field allow (SPDX identifiers, custom, "all rights reserved" for paid content)? How do Foundry VTT, Unreal, Godot, Unity, Roblox, Minecraft, and Defold handle "engine license vs. what you build on it"? Give a recommendation and flag anything needing a lawyer.

**G. Client and editor model (design only, built last).** Structured-data protocol (GMCP-like JSON over WebSocket) for a React player client; declarative panel manifests from fragments; whether editors should be browser-only (per CharacterBinder's Tauri-removal lesson) vs desktop; MCP server so AI coding agents can author fragments and drive editors; accessibility baseline.

**H. Repository and project structure for a solo dev.** Monorepo vs multi-repo (engine, first-party fragments, reference world, Foundry site, shared schema/validation package); keeping any proprietary world entirely outside the engine repo from day one; CI invariants (zero-AI world boots and plays; no setting terms in engine code; manifest round-trip tests; PNG chunk fuzzing); documentation generated from manifests; how to keep a single developer from re-creating v1's convolution (decision-log hygiene, ADRs, scope gates).

**I. Risk register and "do not build" list.** What to explicitly exclude from v1 of the engine and v1 of the Foundry; feature-creep traps; the three or four milestones with pass/fail criteria before the next layer is allowed to start.
